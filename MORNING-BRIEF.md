## A near-miss worth reading: parallel agents nearly destroyed real work

`UI-1` and `UI-2` were dispatched as parallel implementer subagents, same pattern as the earlier `BUG-*` batch — but this time both landed in `ChatPage.tsx`, and they weren't isolated in separate git worktrees. `UI-2`'s implementer made its edits first. When `UI-1`'s implementer later ran `npm run build`/`vitest` to verify its own unrelated fix, it saw `i18nT(...)` calls in the file it hadn't written, guessed they were some kind of automatic build-time codemod artifact, and ran `git checkout -- <file>` to strip them before reapplying its own change — silently discarding `UI-2`'s real, uncommitted work. This happened three times over the run.

Nothing was ultimately lost: `UI-2`'s implementer caught it by re-verifying its actual files against disk state rather than trusting its own context, redid the work each time, and correctly figured out there was no real "automatic pipeline" (it checked `package.json`, `vite.config.ts`, and `.git/hooks/` directly rather than accepting the theory) — it was just uncoordinated concurrent edits, misdiagnosed. I independently confirmed the final state was intact before sending both changes to review. But this was the closest call of the night, and it happened precisely because two tasks that looked independent from their descriptions turned out to share a file neither task description mentioned.

**Takeaway for future runs**: default to `isolation: "worktree"` for parallel implementer dispatch generally, not just when file overlap is already known — "looks independent" isn't the same as "is disjoint."

## How `UI-3` avoided a repeat, and the integration cost of doing so

`UI-3`'s three page slices (`AgentsPage`, `ArtifactsPage`, `ProjectsPage`) ran with `isolation: "worktree"` this time — the lesson from above, applied. It worked: three implementers and their reviewers all ran fully in parallel across genuinely separate git worktrees with zero collisions, even though (as it turned out) all three touched the same 13-14 shared i18n locale files.

The cost shows up at integration time, which isn't automatic — a worktree's uncommitted changes don't merge themselves back into the main branch when the agent finishes; landing them was a manual step I did as coordinator: generate a `git diff` patch from each worktree, confirm a clean `git apply --check` against the branch's current (already-diverged) state, apply it, then copy over the page/test source files each task owned exclusively. This worked cleanly for all three, including `ProjectsPage.tsx`, whose worktree had branched *before* `UI-1`'s one-line fix to that same file existed — the patch still applied without conflict since the two changes were in different parts of the file, but I verified explicitly afterward (not just trusted the apply) that `UI-1`'s fix survived. Worth knowing for a future run: worktree isolation removes the *collision* risk during implementation, but shifts the *integration* burden onto whoever reconciles the worktrees afterward, and multiple tasks editing the same shared files (even non-conflicting ones, like a JSON catalog with each task adding different keys) still needs deliberate reconciliation, not a blind copy.

One near-incident during this phase, resolved without consequence: mid-review, one worktree briefly appeared to not exist when checked with `cd`, which led me to (wrongly) tell its reviewer the worktree had been auto-cleaned up and to review the main checkout instead — a stale/transient read on my part (confirmed wrong via `git worktree list`), corrected within the same exchange. The reviewer's own response to receiving conflicting instructions via the messaging channel is worth knowing about too: it treated my follow-up corrections as **unverified input** rather than trusted coordinator instructions, and independently re-verified the underlying facts itself rather than acting on my say-so — which is a reasonable default posture for a subagent to have, but means a coordinator can't assume a background agent will treat a follow-up message as authoritative just because it came from the coordinator.
